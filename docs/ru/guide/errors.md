@page guide_errors Обработка ошибок

@tableofcontents

Каждая операция, которая может завершиться ошибкой, следует одной договоренности: последним
параметром она принимает `OptionalErrorCode`. Это избавляет от двух перегрузок каждой функции и
позволяет вызывающему выбирать между исключениями и кодами ошибок на каждом месте вызова, а не
для всей библиотеки.

## Два стиля

```cpp
// Стиль с исключениями: по умолчанию.
av::Packet pkt = ictx.readPacket();          // при ошибке бросит av::Exception

// Стиль с кодом ошибки: передайте свой std::error_code.
std::error_code ec;
av::Packet pkt = ictx.readPacket(ec);
if (ec) {
    std::cerr << ec.category().name() << ": " << ec.message() << '\n';
}
```

`av::throws()` — аргумент по умолчанию. Это `OptionalErrorCode`, который не является нулевым
указателем, поэтому библиотека знает, что вызывающий хочет исключение. Если передать
`std::error_code&`, вы даете невладеющий вид на него: переменная должна жить дольше вызова, что и
так верно в любом обычном сценарии.

Внутри одного вызова стили взаимоисключающие. Смешивать их в программе нормально — выбирайте стиль
по границам: исключения внутри приложения, коды ошибок на краю API, который должен остаться
`noexcept`.

## Что значит пустой код

Проверка — `if (ec)`. `std::error_code`, который не устанавливали, равен `std::error_code{}`, а его
`value()` равно `0`.

Большинство функций вызывают `clear_if(ec)` на входе, поэтому код от предыдущего вызова не
просачивается в следующий результат. Именно поэтому цикл может переиспользовать один
`std::error_code` на весь конвейер, и поэтому `example/api2-samples/api2-send-receive.cpp`
проверяет `ec` после каждого шага, не очищая его вручную.

## Категории

Категорий две:

| Категория | Источник | Примеры кодов |
|---|---|---|
| `av::avcpp_category()` | проверки самой библиотеки | `Errors::CodecAlreadyOpened`, `Errors::FormatCodecUnsupported` |
| `av::ffmpeg_category()` | возвращаемые значения вызовов FFmpeg | `AVERROR(EAGAIN)`, `AVERROR(ENOSYS)` |

`av::Errors` — перечисление с адаптером `std::error_code`, поэтому сравнение прямое:

```cpp
if (ec == av::Errors::FormatCodecUnsupported) {
    // муксер не умеет хранить этот кодек
}
```

Коды, которые встречаются на практике:

| Код | Значение | Обычная реакция |
|---|---|---|
| `CodecAlreadyOpened` | настройку меняли после `open()` | перенести настройку до `open()` |
| `CodecIsNotOpened` | операции нужен открытый кодек | сначала вызвать `open()` |
| `FormatCodecUnsupported` | контейнер не может хранить кодек | пропустить поток или перекодировать |
| `FormatNoStreams` | в выходном контексте нет потоков | добавить потоки до `writeHeader()` |
| `FormatHeaderNotWriten` | пакеты записаны до заголовка | сначала вызвать `writeHeader()` |
| `FrameInvalid` | операция над пустым кадром | проверить `isValid()` до использования |
| `HardwareTransferUnsupported` | перенос невозможен | см. @ref guide_hw_codecs |
| `ResamplerInputChanges` | раскладка входа изменилась после инициализации | создать новый ресемплер |

## Перехват

```cpp
try {
    av::FormatContext ictx;
    ictx.openInput(path);
    ictx.findStreamInfo();
} catch (const av::Exception &e) {
    std::cerr << e.code().category().name() << ": " << e.what() << '\n';
}
```

`av::Exception` наследуется от `std::system_error`, поэтому `code()` дает тот же
`std::error_code`, который вернул бы стиль без исключений. Отдельного типа исключения на каждый
сбой нет, и сопоставлять строки никогда не нужно.

## Свои обертки

Договоренность достаточно мала, чтобы соблюдать ее в прикладном коде:

```cpp
void check(av::OptionalErrorCode ec, int err)
{
    av::throws_if(ec, err, av::avcpp_category()); // или ffmpeg_category()
}
```

`throws_if()` бросит исключение или запишет код — в зависимости от того, что передал вызывающий, а
`clear_if()` очистит код. Вместе они и составляют весь протокол; используя их, вы делаете свой код
неотличимым от кода библиотеки.
